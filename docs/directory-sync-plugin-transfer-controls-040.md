# Remembered speed limit, low-rate copying and cancellation — 0.4.0

Development follow-up, 2026-10-21. No SDK change or SMB test.

## Host comparison

Reviewed the host at `e1efc2863e4bbee5ee78f27cacc8d8bcf7ed31d4`: `src/worker.cpp`, `COperations::CalcLimitBufferSize` and `AddBytesToSpeedMetersAndTFSandPS`; `src/worker.h`, `HIGH_SPEED_LIMIT`; and `src/dialogs.cpp`, the speed-limit and `IDCANCEL` handlers in `CProgressDialog`.

The core shrinks actual I/O blocks below the configured rate, then waits as needed. It caps braking after an in-flight speed reduction rather than charging many minutes for an already transferred block. Its default last-used positive value is 1 MiB/s, stored in `Configuration.LastUsedSpeedLimit`. It remembers a convenient number; this is distinct from automatically enabling a limit for every new transfer. The plugin now remembers both the effective limit/unlimited selection and the last positive value, as requested.

The core's progress Cancel pauses work and opens a standard Yes/No question. Repeated Escape does not dismiss that question. The plugin now calls the existing SDK `SalMessageBox` service directly, using UTF-8 question/title strings, host-localized buttons and host appearance. No restores the previous pause request, Yes calls the existing cooperative Stop. No is the default button. Host shutdown, forced unload and main-preview Stop/Close retain unconditional cancellation. The standalone harness uses native `MessageBoxW` because it has no host service.

An initial live candidate used the bundled wide dark-message-box wrapper. Source review found that its TaskDialog path unconditionally enables cancellation, which differs from the host's Escape policy. The final implementation uses the actual host message-box API instead; no vendored UI changes are needed.

The host worker/queue is private and cannot be reused through the pinned SDK. These changes use its buffering principle, not a private API or a claim of identical implementation. Shared-core transfer integration remains a future API-dependent task.

## Implementation

- Store validated 64-bit `TransferSpeedV1` and `LastTransferSpeedV1` binary values through the existing configuration API. Zero means unlimited; positive values are bounded by 1 TiB/s. Missing/malformed settings fall back to unlimited and a 1 MiB/s suggestion. Settings are global, not profile fields. Accepting the speed dialog saves them; Cancel leaves them unchanged. A new operation initializes its active limit from the remembered value.
- Replace `CopyFileEx` callback-only throttling with buffered `ReadFile`/`WriteFile` copying of the main data and all enumerated named data streams into the owned stage. Select the next I/O block dynamically: at most 1 MiB without a limit, or roughly 100 ms of the configured rate (at least one byte). At 4 KiB/s the maximum block is 409 bytes. Windows/system buffering still exists; this is cooperative rate control, not a hard real-time guarantee.
- Preserve creation/access/write times and the existing verified data, ADS, selected attributes, destination DACL, stage identity, publication and recovery/journal rules. Verification reads remain unrestricted. Copying is still not a full NTFS backup or transactional rollback.
- A changed rate discards old throttle debt and limits transitional braking to one second. It cannot undo bytes already written. The displayed rate sample resets on an accepted change, and the current nonzero limit remains visible even when the instantaneous sample is zero.
- Add a guarded cancellation question for the progress Cancel button, Escape and title-bar Close. Pause requests remain cooperative; an in-flight write or protected publication/journal boundary may complete before the worker observes the pause. Closing the owner while the question is open must release the nested native dialog. Use the existing callback lifetime guard for reentrant forced unload.
- Redirect real `WriteFile` calls in the test-only disk-full injector instead of the removed `CopyFileEx` boundary. Inject genuine partial staging bytes, retain cleanup-failure coverage, and count known partial writes even when Windows reports failure. No fault-injection code ships in the plugin.
